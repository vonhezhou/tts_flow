# tts_flow 架构与边界

## 定位

`tts_flow` 是一个面向 Dart 与 Flutter 应用的**在线 TTS 音频流接入框架**。

它解决的重点是：以尽可能低的首包播放延迟，将在线 TTS 服务产生的音频稳定地交付给播放、文件保存或其他应用侧消费者。框架提供统一的引擎适配、请求队列、格式能力描述、取消及事件语义，并允许同一份合成音频发送到多个输出。

它不是通用音频处理、混音或媒体编排框架。

## 目标

- 简化 Flutter/Dart 应用接入不同在线 TTS 服务的工作。
- 将在线 TTS 的流式音频尽快交给播放器。
- 在播放器支持源格式时，保留压缩音频直通路径，避免在 Dart 层无必要地解码。
- 支持一份合成流按需发送到多个输出，例如扬声器、原始音频文件和应用自定义消费者。
- 为有特殊需求的用户提供自定义输出接口，而不把音频处理框架内建到核心中。
- 保持纯 Dart 核心与 Flutter 播放适配分离。

## 非目标

以下能力明确不属于 `tts_flow` 的职责：

- 通用音频处理图、动态节点路由或自动拓扑规划。
- 多路实时混音、背景音乐、ducking、交叉淡入淡出或麦克风处理。
- 自动插入任意编解码、重采样或 DSP 节点。
- 抽象所有平台系统 TTS 的行为及其平台差异。

需要上述能力的应用，应在 `tts_flow` 外部接入专门的实时音频处理框架。`tts_flow` 负责提供清晰的音频流边界，而不是重复实现媒体引擎。

## 核心模型

```text
文本请求
  → TtsFlow（队列、生命周期、格式选择）
  → TtsEngine（在线 TTS，产出音频块）
  → TtsOutput（播放、保存或应用自定义消费）
```

- `TtsEngine`：在线服务的适配层。它将文本请求转换为有序的 `TtsChunk` 流，并声明真实支持的输出格式与音色能力。
- `TtsFlow`：服务编排层。它管理请求队列、服务级默认设置、格式协商、暂停/停止语义及事件。
- `TtsOutput`：音频消费边界。它可以是扬声器、文件、内存、网络或应用实现的自定义 sink。
- `MulticastOutput`：将同一份音频流同步扇出到多个输出；所有分支都在合成的背压路径中。
- `PrioritizedOutput`：一个主输出加零个或多个旁路辅助输出；只有主输出参与格式协商和背压。

### Output 生命周期

传给 `TtsFlow` 的默认 Output 与请求级 Output 都由该 Flow 管理：Flow 会在某个 Output 首次开始写入前初始化它，并在 Flow 销毁时释放它。一个 Output 实例不应同时交给多个 Flow 使用。

请求级 Output 的惰性初始化使调用方可以按请求选择单路或多路输出，而不用手动拼接 Output 的初始化时机。

同一个 Flow 对同一个 `TtsOutput` 的写入严格串行：前一个请求必须完成 `finishWrite()` 或 `cancelWrite()`，下一个请求才会调用 `startWrite()`。因此 `TtsOutput` 只需维护一个活跃写入，不承担并行合成、并行写入或音频图调度。

这不等同于“设备上没有任何旧音频仍在播放”。`SpeakerOutput` 等播放 Output 可以在写入结束后保留某个 request 的物理播放控制与事件关联；该能力只用于观测和控制已交给设备的音频，不承诺多个请求混播。

## 低延迟原则

低延迟的默认路径应当是：

```text
在线 TTS 产生 MP3 / Opus / AAC
  → 支持该格式的播放器
  → 直接播放
```

格式选择优先考虑播放器能够原样接受的格式。为了某个额外分支需要 PCM，不应让整个请求统一解码为 PCM。

所有分支都必须收到完整流时，可使用 `MulticastOutput`：

```text
在线 TTS（MP3）
  ├─ SpeakerOutput：MP3 直通播放
  ├─ Mp3FileOutput：MP3 原样保存
  └─ Decoder → WavFileOutput：仅这个分支解码为 PCM/WAV
```

`MulticastOutput` 会等待每个分支处理当前 chunk。因此，扬声器与需要解码、写盘或进行耗时处理的分支不应直接放在同一个 `MulticastOutput` 中，除非调用方明确接受该分支反向增加播放延迟。

播放优先、附带可降级观察者时，使用 `PrioritizedOutput`：

```text
在线 TTS（MP3）
  ├─ primary: SpeakerOutput：MP3 直通播放，参与背压
  └─ auxiliaries: 录制 / 指标 / 应用处理：只接收旁路通知
```

`PrioritizedOutput` 只等待 primary；辅助输出不参与格式协商，也不阻塞合成或播放。它不替辅助输出管理队列、重试、丢弃或收尾：辅助实现必须自行处理异步工作、顺序和资源生命周期。同步的 CPU 密集型辅助实现仍会阻塞 Dart isolate，因此也不应放在播放关键路径。

这仍不是通用处理图，而是一个单一上游流配合少量、显式的输出包装器。转换应只在调用方明确需要时发生。

## 多输出与自定义处理

多输出的约束是：一次在线合成默认只产生一种源格式。每个输出或输出包装器应声明它接收的输入格式；服务只选择所有分支都能接收的源格式。

若某个分支需要不同格式，它应在自身内部完成明确声明的转换。例如，一个解码输出可以接收 MP3，然后向其下游输出 PCM。框架不应隐式猜测、插入或组合处理步骤。

高级用户可通过实现 `TtsOutput` 接收 `TtsChunk`，从而把流接入自己的处理系统。自定义输出应保留块顺序、尊重取消、声明可接受的格式，并自行定义其处理失败策略。若它是 `PrioritizedOutput` 的辅助分支，则应实现 `TtsAuxiliaryOutput`，并自行处理异步工作和顺序。

对于更复杂或可靠性要求更高的实时处理，应用可直接消费 `TtsRequestHandle.chunks`，将其接入应用侧或专门的实时处理系统。它是单订阅流；`TtsRequestHandle` 本身只是同一条流的 view，二者只能择一订阅。调用方应在 `speak()` 后立即把这一个消费者接到其处理系统，而不是把它当作核心包提供的广播或隐式 fan-out。

若应用侧要继续分发给多个消费者，该系统自行决定缓存、丢弃、重试、重采样与 DSP 策略；`tts_flow` 不管理这些策略。需要核心包直接管理的多输出时，可靠且背压耦合的分支使用 `MulticastOutput`，播放优先的旁路观察者使用 `PrioritizedOutput`。

## 系统 TTS 的边界

系统 TTS 与在线 TTS 的能力模型不同：

```text
在线 TTS：文本 → 可访问的音频字节流 → 播放 / 保存 / 分发
系统 TTS：文本 → 平台扬声器播放
```

多数系统 TTS API 不会提供可复用的实时音频字节流。因此，系统 TTS 不能诚实地满足在线 TTS 的多输出、原始文件保存和自定义音频处理契约。

`tts_flow` 不应强行依赖或封装系统 TTS。Flutter 应用可在应用层直接使用如 `flutter_tts` 的独立包，并按业务需求选择在线 TTS 或系统 TTS。未来可以提供示例说明在线服务不可用时的应用层 fallback，但不应把该依赖加入核心包。

## 稳定扩展边界

为了让消费者能够接入外部播放器或音频处理系统，核心接口需要稳定地表达：

- 音频块字节及其 `TtsAudioSpec`；
- 块顺序与请求标识；
- 结束、失败和取消；
- Output finalize 后的 `AudioArtifact`，以及它与物理播放完成的区别；
- 格式能力；
- 合成完成与物理播放完成的不同事件。

队列/合成控制与物理播放控制也必须分离。队列暂停只影响后续合成请求的启动；已交给设备的音频由 `TtsRequestHandle.pausePlayback()`、`resumePlayback()` 与 `stopPlayback()` 控制。可控制播放的 Output 必须在音频提交完成后继续保留 request 到 playback 的关联，直到物理播放终止。

`TtsRequestHandle.synthesisResult` 是请求合成与 Output 写入的终态结果：成功时携带 `TtsOutput.finishWrite()` 返回的 `AudioArtifact`，停止或失败时携带对应原因。它始终正常完成，避免仅播放的调用方因未监听 result 而得到未处理的 Future 错误。它不等待设备实际播完；物理播放仍通过 playback 事件和控制接口表达。

每次 `speak()` 都由 Flow 生成唯一、不透明的 `requestKey`，它是 engine、chunk、output write 和物理播放路由的唯一键。调用方可传入 Android 风格的 `utteranceId`，它只用于业务关联并随 Flow 事件与请求句柄公开；该值允许重复，绝不能参与底层会话寻址。
- 可选的、按请求连续的物理播放时间轴；支持该能力的 backend 可用于
  句子级字幕或阅读高亮，但它不是所有 backend 的强制职责。

在线服务若返回可靠的句子时间边界，可发出 `TtsSentenceCueChunk`。
其中的文本范围相对于 `TtsRequest.text`，音频时间相对于该请求的播放
起点；阅读应用负责再映射到书籍章节的原文范围。没有可靠时间边界的
服务不应猜测 cue，应用可降级为高亮整个请求文本。

框架的职责止于这些边界。复杂音频系统可通过自定义 `TtsOutput` 或适配层消费这些信息，而无需改变 `tts_flow` 的核心定位。

## 演进准则

后续设计与代码变更应优先回答以下问题：

1. 是否缩短了在线 TTS 的首包到播放时间？
2. 是否保持了播放器可用格式的直通能力？
3. 是否让简单的“在线 TTS + 播放”接入保持简单？
4. 是否把复杂音频编排留在框架外部？
5. 是否仅在调用方显式要求时才引入解码或其他 CPU 音频处理？

如果一项设计主要服务于通用媒体编排，而不能直接改善上述目标，它通常不应进入 `tts_flow` 核心。

Flutter 平台播放实现的专门约束与演进方案见
[JustAudioBackend 设计说明](just_audio_backend.md)。
